## Batch 1 - Core Model, Schema, Type and Config Extensions

**Branch:** feat/v2-telemetry-schema | **PR:** #47 | **Status:** MERGED

### What was changed and why

#### firmware/esp32/config.h

The existing config.h only covered the v1 hardware: Wi-Fi credentials, old API URL, DHT_PIN (GPIO4), LDR_PIN (GPIO34), MPU6050_SDA/SCL, and POLL_INTERVAL_MS. This was written for a single ESP32 reading two sensors.

The v2 spec introduces 11 sensors and multiple output components. Rather than replacing the file (which would break the existing main.ino sketch that references DHT_PIN and WIFI_PASSWORD), all new definitions were appended after the existing content under a clear `v2.0 additions` separator comment.

Key design decisions made during this step:

- **LDR pin conflict**: The v1 spec put LDR on GPIO34. The v2 spec moves LDR to GPIO33 and gives GPIO34 to the MQ-2 analog output. To avoid redefining LDR_PIN (which would break the old main.ino), a new `LDR_V2_PIN 33` was added. The old `LDR_PIN 34` remains untouched for backward compatibility. New firmware modules (in sensors/) use LDR_V2_PIN.

- **DS18B20 / DHT22 overlap**: Both the v1 DHT22 and v2 DS18B20 use GPIO4. `DS18B20_PIN 4` was added as a new define pointing to the same physical pin. The v2 node physically replaces DHT22 with DS18B20 on that GPIO, so in practice only one is connected at a time.

- **I2C naming**: The v1 config had `MPU6050_SDA` and `MPU6050_SCL` as the I2C bus names. The v2 config adds `I2C_SDA` and `I2C_SCL` as canonical aliases pointing to the same GPIOs (21 and 22). The v2 sensor modules use I2C_SDA/SCL to make it clear they share a common bus rather than being exclusive to the MPU6050.

- **Serial ports**: Two extra UART channels were added (NANO_RX/TX on UART1, STM32_RX/TX on UART2). UART0 is kept for the USB debug console. The Nano communicates at 9600 baud (its default). The STM32 communicates at 115200 baud (faster because it sends 100Hz FFT results compressed to one line per second).

- **Alert thresholds**: Thresholds were set conservatively. TEMP_WARNING_C=40.0 and TEMP_CRITICAL_C=60.0 are appropriate for generic industrial equipment but will need calibration once real readings are collected.

#### backend/app/models/telemetry.py

The existing ORM model had: id, device_id, temperature, humidity, vibration_x, vibration_y, vibration_z, light_level, anomaly_score, is_anomaly, recorded_at. It was written for the v1 three-sensor ESP32.

Eighteen new columns were added:

| Column | Type | Reason |
| --- | --- | --- |
| node_type | String(20) | Identifies which physical board sent the reading. Needed because the same API endpoint accepts POSTs from all four node types. |
| pressure | Float | BME280 outputs temperature + humidity + pressure as a unit. Leaving pressure out of the model would discard barometric data silently. |
| gyro_x, gyro_y, gyro_z | Float | MPU6050 provides both accelerometer and gyroscope. Gyro data is needed for rotational anomaly detection. |
| bus_voltage, current_ma, power_mw | Float | INA219 three-in-one current monitor. All three are stored together so electrical health checks are complete. |
| ir_temperature | Float | MLX90614 gives contactless surface temperature. Stored separately from BME280 temperature so hot-spot detection does not interfere with ambient reading. |
| distance_mm | Float | VL53L0X shaft displacement / proximity. Alert fires when value drops below DISTANCE_ALERT_MM. |
| gas_level, gas_alert | Float, Boolean | MQ-2 outputs both an analog level and a digital threshold signal. Both are stored so the backend can recompute the threshold if needed without re-reading hardware. |
| shaft_angle, shaft_rpm | Float | AS5600 magnetic encoder. Angle gives absolute position; RPM is derived from angle change over time. |
| sound_level | Float | MAX4466 microphone ADC level. Acoustic signatures correlate with bearing wear. |
| contact_temp | Float | DS18B20 precision contact temperature distinct from BME280 ambient and MLX90614 IR readings. |
| moisture_level, water_detected | Float, Boolean | FC-28 water ingress sensor. Both raw level and binary alert are stored. |
| fft_peak_hz, vib_magnitude | Float | STM32 FFT output forwarded by the ESP32 after parsing UART. These are never sent by the STM32 directly; the ESP32 parses the STM32's UART string and merges these fields into the main telemetry payload. |

The `String` import was added to the SQLAlchemy imports line for node_type. All other types were already imported.

All columns are nullable because nodes with fewer sensors should still pass schema validation. A Pico 2W node only sends temperature, humidity, pressure, and light_level; all other fields will be NULL for its rows.

#### backend/app/schemas/telemetry.py

Both Pydantic models (TelemetryIngest and TelemetryResponse) were extended to match the updated ORM model.

TelemetryIngest uses `float | None = None` syntax (Python 3.10+ union shorthand) to keep all sensor fields optional. This means firmware nodes with partial sensor coverage can POST successfully without the backend rejecting the payload.

TelemetryResponse now exposes all 18 new fields to API consumers. The dashboard and ML service need these fields in the response to drive visualisations and anomaly scoring.

#### frontend/types/index.ts

The TypeScript Telemetry interface was extended to mirror the backend schema. All new fields use `number | null` for floats and `boolean | null` for nullable booleans. The existing `is_anomaly: boolean` was kept non-nullable (the backend always sets a default).

Grouped with inline comments by sensor category (BME280, MPU6050, INA219, etc.) to make the interface scannable.

#### backend/requirements.txt

Two packages added:

- `python-dotenv==1.0.1` - needed by ML scripts (train.py, evaluate.py) that run standalone outside FastAPI and need to load .env files manually. FastAPI's pydantic-settings already handles .env loading in the app, but standalone scripts need dotenv explicitly.
- `pytest-asyncio==0.23.6` - needed for async FastAPI test functions that use async database sessions.

#### .gitignore

Three groups of patterns added:

- `*.elf, *.bin, *.hex, *.map` - Arduino IDE and GCC build artefacts. These are generated in the firmware build folders and are typically large binary files. They should never be committed.
- `*.DBK, *.LKS, *.SDF` - Proteus EDA tool backup and simulation files. The PCB schematic will be developed in Phase 2/3; when Proteus generates these files they should be ignored.
- `backend/ml/features.csv, backend/ml/telemetry.csv` - ML training data exports generated by the train.py preprocessing pipeline. These can be large and should be regenerated from the database rather than versioned.

## Batch 2 - ESP32 v2 Firmware Sensor/Output/Comms Modules

**Branch:** feat/esp32-v2-firmware | **PR:** pending | **Status:** files created, awaiting commit

### What was created and why

The existing firmware/esp32/ folder contained: main.ino (old v1 sketch reading DHT22/MPU6050/LDR), dht22.ino, mpu6050.ino, ota.ino, config.h. These were structured as flat .ino files in the Arduino IDE style, suitable for a simple two-sensor node.

The v2 ESP32 has 11 sensors, 4 output types, and 2 serial connections. A flat .ino structure would become unmanageable. The solution was to introduce a structured subfolder layout (sensors/, outputs/, comms/) with .h/.cpp pairs for each module, and a new esp32.ino as the v2 main sketch. The old main.ino remains untouched for reference.

#### sensors/ - 20 files (10 sensor pairs)

Each sensor gets its own .h (struct definition and function declarations) + .cpp (implementation). This separation means:
- The compiler only sees sensor-specific library headers where they are actually used
- Each sensor module can be unit-tested independently
- Adding or removing a sensor means touching one pair of files, not the main sketch

Sensor-by-sensor design decisions:

**BME280 (bme280.h/cpp)**
Uses the Adafruit_BME280 library. The init function probes address 0x76 first (BME280_ADDR), then falls back to 0x77, because some BME280 breakouts are wired differently. If neither responds the error is printed but the program continues rather than halting - a partial reading is better than no reading when other sensors work.

**MPU6050 (mpu6050.h/cpp)**
Uses the Adafruit_MPU6050 library. Accelerometer values are converted from m/s^2 to g-units by dividing by 9.80665 because the telemetry schema and dashboard both expect g-units. Gyroscope is left in rad/s as delivered by the Adafruit library.

**INA219 (ina219.h/cpp)**
Uses the Adafruit_INA219 library. Power_mw is computed as bus_voltage * current_ma rather than using the library's getPower_mW() call. The reason: getPower_mW() can return stale values on shunt overflow. Computing it locally from the fresh bus_voltage and current_ma reads ensures consistency.

**MLX90614 (mlx90614.h/cpp)**
Uses the Adafruit_MLX90614 library. Returns objectTemperature() (the surface being measured) rather than ambientTemperature() because the IR sensor is pointed at machinery, not the environment.

**VL53L0X (vl53l0x.h/cpp)**
Uses the Adafruit_VL53L0X library. Returns 0 on timeout/error rather than crashing - a distance of 0 is distinguishable from real readings in most industrial contexts and will not false-trigger alerts.

**MQ-2 (mq2.h/cpp)**
Reads MQ2_ANALOG_PIN via analogRead() for the continuous level. The digital pin (MQ2_DIGITAL_PIN) is configured with INPUT_PULLUP because the MQ-2 comparator has an open-collector output that needs an external pull-up. gas_alert is TRUE when the digital pin reads LOW (active-low convention on the MQ-2 board).

**AS5600 (as5600.h/cpp)**
Reads angle registers 0x0C and 0x0D via Wire directly (no library) because the AS5600 register map is simple and adding a full SparkFun library for two register reads is unnecessary overhead. The raw 12-bit value (0-4095) is converted to degrees (0-360). RPM is calculated from the delta angle over a 100ms interval with wrap-around handling (shortest angular distance) so the RPM remains correct even as the shaft crosses 0/360 degrees.

**DS18B20 (ds18b20.h/cpp)**
Uses DallasTemperature + OneWire on DS18B20_PIN. waitForConversion(false) is called so the sensor initiates a conversion without blocking the main loop for 750ms at 12-bit resolution. The main loop reads the last completed conversion value rather than waiting for a fresh one on each cycle.

**LDR + MAX4466 (ldr.h/cpp)**
Both are analog-only sensors with no I2C protocol, so they share a module. readLDR() reads LDR_V2_PIN (GPIO33 in v2). readMAX4466() reads MAX4466_PIN (GPIO32). Raw ADC values are returned as floats without scaling - scaling is left to the dashboard layer.

**FC-28 (fc28.h/cpp)**
Reads FC28_PIN analog value. water_detected is true when raw < WATER_THRESHOLD because the FC-28 is a resistive sensor: more water = lower resistance = lower ADC reading. The logic is counterintuitive (low number = wet) so this is documented in a comment.

#### outputs/ - 8 files (4 output pairs)

**OLED (oled.h/cpp)**
Uses Adafruit_SSD1306 + Adafruit_GFX at OLED_ADDR (0x3C). displayTelemetry() shows a 4-line layout because 64px / 8px text size = 8 possible lines, but 4 lines of readable data is better than 8 lines of squished text. Line assignment: temperature/humidity/pressure, vibration axes, voltage/current, alert status.

**Buzzer (buzzer.h/cpp)**
Uses Arduino's built-in tone()/noTone() which handles PWM frequency internally. The BuzzerPattern enum maps to specific beep sequences: PATTERN_WARNING = 2 short beeps, PATTERN_CRITICAL = 3 rapid beeps repeated twice. The buzzer is silenced between sequences so patterns are distinguishable.

**RGB LED (rgb_led.h/cpp)**
Uses Adafruit_NeoPixel on RGB_LED_PIN with RGB_LED_COUNT pixels. All pixels are set to the same color for uniform indication: green = normal operation, amber = warning threshold crossed, red = critical alert or anomaly detected.

**Relay (relay.h/cpp)**
The relay module is active-low: writing LOW turns a relay ON, writing HIGH turns it OFF. This matches the typical opto-isolated 4-channel relay module wiring convention. The RELAY_CH1-4 pins default HIGH (relays off) in initRelay(). triggerRelay() takes a RelayChannel enum index to prevent out-of-bounds pin access.

#### comms/ - 6 files (3 comms pairs)

**WiFi Manager (wifi_manager.h/cpp)**
Stores the last SSID and password in static variables so reconnectWiFi() can retry without the caller passing credentials again. The connection loop polls every 500ms up to WIFI_TIMEOUT_MS=10000ms (20 attempts). On timeout, "WIFI FAILED" is printed but the node continues running - local sensor readings and serial output still work even without network connectivity.

**HTTP Client (http_client.h/cpp)**
Returns the HTTP status code as an int so the caller (esp32.ino's postTelemetry()) can log success vs failure without inspecting string payloads. Returns -1 when WiFi is not connected. Always calls http.end() to release sockets - not calling end() on ESP32 causes connection pool exhaustion after a few hundred POSTs.

**Serial Parser (serial_parser.h/cpp)**
Both NanoData and STM32Data structs have a `valid` flag. If parsing fails for any reason (malformed string, missing field), valid is left false and the caller skips merging those fields into the JSON payload. This prevents corrupted readings from being forwarded to the API.

NanoSerial parsing: CSV format "TEMP:28.5,HUM:55.2,PRES:1013.2,LIGHT:340,MOIST:210,WATER:0" is extracted by finding each key prefix, then reading the float up to the next comma.

STM32Serial parsing: "VIB:0.14,0.08,9.79,MAG:9.80,FFT_PEAK:12.5Hz" - the FFT_PEAK value is extracted, the "Hz" suffix is stripped before toFloat() conversion. vib_magnitude comes from the MAG field.

#### esp32.ino - new v2 main sketch

The new esp32.ino sits alongside the old main.ino. The Arduino IDE will compile whichever sketch the user has open. The old main.ino is not modified so it remains functional for testing on v1 hardware.

Key architectural decisions in esp32.ino:

- Three independent time intervals: TELEMETRY_INTERVAL_MS (5s for API POST), OLED_UPDATE_MS (1s for display), SERIAL_POLL_MS (implied every loop() for serial reads). The millis()-based timing avoids blocking delay() calls that would desynchronise the intervals.
- Serial poll happens every loop() iteration rather than on an interval because UART data can arrive faster than 100ms and missing bytes leads to malformed string parsing.
- checkThresholds() is called after every sensor read cycle (every 5s) to ensure outputs reflect the latest readings promptly.
- The STM32 FFT data validity flag (stm32Data.valid) is checked before adding FFT fields to the JSON payload. If the STM32 node is offline or hasn't sent data yet, those fields are simply omitted from the payload - the backend accepts partial payloads.

#### firmware/esp32/README.md

Wiring tables for all 11 sensors and 4 output types, with GPIO numbers, I2C addresses, and notes on shared bus connections. Power infrastructure section explains the 12V -> LM2596 -> 5V -> AMS1117 -> 3.3V chain and where each voltage rail feeds.

### What was created and why

#### backend/app/models/__init__.py, routes/__init__.py, schemas/__init__.py, services/__init__.py

Python requires __init__.py files for a directory to be treated as a package. Without them, relative imports fail in some Python configurations and IDE tooling (e.g. pylance) cannot resolve imports. All four are intentionally empty with a one-line comment explaining why - this is the standard pattern for FastAPI apps where modules are imported directly by name.

#### backend/app/services/audit_service.py

Audit logging was designed as a standalone service (not embedded in route handlers) for two reasons:

1. Separation of concerns: route handlers should not know about audit requirements. If auditing is ever disabled or swapped for a different sink (e.g., CloudWatch), only audit_service.py changes.
2. Silent failure: audit log writes use try/except and print to stderr on failure but never raise. A database write failure on the audit log should never crash a business-critical API request.

The log_action() function uses raw SQL (db.execute) with a text() query rather than an ORM model for the audit_log table. This avoids circular imports (the audit log model would need to import from the same db.py as the other models) and keeps the audit table independent - it can be moved to a separate database later without changing the service.

Fields stored: id (UUID), user_id, action (e.g. "ticket.create"), resource (table name), resource_id, detail (free text), created_at (UTC-aware timestamp).

#### backend/ml/evaluate.py

Skeleton only - four function signatures with full docstrings and NotImplementedError bodies. The functions are:

- load_model(model_path) - loads a joblib-serialised Isolation Forest from disk
- evaluate_precision_recall(model, X_test, y_true) - returns dict with precision, recall, F1 using sklearn metrics
- plot_anomaly_distribution(scores, output_path) - saves a matplotlib histogram of anomaly scores to file
- generate_report(model_path, data_path, output_path) - end-to-end pipeline: load data, load model, evaluate, plot, save report

These are NotImplementedError because no real hardware data exists yet. The plan (Week 10) is to collect 2-4 weeks of baseline readings and then implement the evaluation pipeline against that data.

#### backend/migrations/001_initial_schema.sql

The full SQL schema for all seven tables. Key design decisions:

- All primary keys use gen_random_uuid() rather than sequences. UUIDs are used because the device_id is also a UUID (matching the firmware config where DEVICE_ID is a string representation of a UUID). Consistency across the schema makes joins predictable.
- All timestamp columns use TIMESTAMP WITH TIME ZONE (TIMESTAMPTZ). The PostgreSQL docs recommend TIMESTAMPTZ for all timestamps that represent moments in real time. It stores UTC internally and converts on read based on the session timezone.
- ON DELETE CASCADE on telemetry.device_id means that deleting a device also deletes all its telemetry rows. This prevents orphaned rows that would cause queries on device-linked data to silently return stale data.
- ON DELETE SET NULL on tickets.device_id and tickets.alert_id means a ticket survives the deletion of its linked device or alert - tickets represent human work that should persist for audit/history purposes even after the associated hardware is decommissioned.
- Eight index statements cover the most common query patterns: device-filtered telemetry, time-range queries, anomaly filtering, device-filtered alerts, alert resolution status, ticket status, audit log user queries, audit log time-range.
- The audit_log table does not have a foreign key on user_id (stored as VARCHAR not UUID). This is intentional: audit entries should survive user account deletion. A FK would prevent deletion of user records unless audit rows were deleted first, which defeats the purpose of a tamper-evident audit log.

#### backend/.env.example

All 15 environment variables documented. Optional integrations (Discord webhook, SMTP email) are left blank with comments explaining they disable the integration when empty, matching the settings.py logic (discord_webhook_url="" disables Discord alerts).
