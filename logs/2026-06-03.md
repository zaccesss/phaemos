### 41. About + blog + changelog + docs hub pages (PR 115)

**Goal:** The platform had no public-facing information pages - no way to explain what it is, how it works, or where to find documentation. Steps 29, 33, and 34 of the plan.

**Design decisions:**

- `react-markdown` chosen over a custom markdown parser because the changelog page needs to render an existing `.md` file from the repo root. Server-side with `fs.readFileSync` at build time keeps the page static with zero runtime overhead.
- `@tailwindcss/typography` installed alongside `react-markdown` so the rendered markdown gets proper prose styling (heading hierarchy, code blocks, lists) without writing a custom stylesheet. The `prose` classes are only applied on the two markdown-rendered pages (changelog and blog post detail) - not on the about or docs hub pages which use hand-crafted Tailwind layouts.
- Blog post metadata (title, date, slug, excerpt, tags) is kept in two places: the markdown frontmatter (for the post page) and a hardcoded `POSTS` array in `blog/page.tsx` (for the index). Duplicating it is intentional - reading frontmatter from all files on every request just to render an index would be wasteful for a static list. If the blog grows past ~10 posts, a proper content pipeline (gray-matter + generateStaticParams) would be the upgrade path.
- `parseFrontMatter()` is a small inline parser rather than a dependency like `gray-matter`. Three fields to parse - pulling in a library for that is unnecessary complexity.
- Email aliases used correctly throughout: `hello@phaemos.com` on the about page (landing-facing), `contact@phaemos.com` for general enquiries, `dev@phaemos.com` for technical questions, `support@phaemos.com` on the docs page. None of the new pages use a personal email address.
- Changelog page reads `../../CHANGELOG.md` relative to `process.cwd()` (which is `frontend/` at Next.js build time). Wrapped in a try/catch so a missing CHANGELOG gracefully degrades to a "not available" message rather than a build failure.
- Sidebar updated: "Changelog" and "Docs" added as a secondary nav section (smaller text, visually separated from the primary nav). Footer links updated to include About and Blog, converted from `<a>` to `<Link>` components to satisfy the `@next/next/no-html-link-for-pages` ESLint rule.
- All three blog posts have substantive content - not lorem ipsum. Post 1 explains the project and differentiators vs ThingsBoard/Grafana/Node-RED. Post 2 explains the Isolation Forest model, training approach, anomaly score threshold, and limitations. Post 3 is a hardware tour covering all four nodes and their sensor roles.

### 42. Status page frontend (PR 116)

**Goal:** The `/status` link in the Sidebar footer went nowhere. The backend `GET /status` endpoint (added in PR 96) returns live database and Redis health, but there was no frontend page consuming it.

**Design decisions:**

- `'use client'` page with `useEffect` + `setInterval` for 30s polling. The page has no useful static content to pre-render - the entire point is a live health check - so SSG would be wrong here.
- `fetch` calls `NEXT_PUBLIC_API_URL/status` with `cache: 'no-store'` to bypass Next.js fetch caching. Without this the response would be stale on every visit.
- Three component rows (API, Database, Cache) map directly to the three keys the backend returns. Each shows a coloured pill badge: green for `ok`, red for `error`.
- Overall banner uses a left border colour and dot indicator: green for operational, pulsing amber for degraded, red for error/unreachable. The pulse on amber draws the eye without being alarming.
- `middleware.ts` updated to add `/status` (and the other public pages from PR 115 that were missed: `/about`, `/blog`, `/changelog`, `/docs`, `/privacy`, `/terms`) to `PUBLIC_PATHS`. Without this, all those pages redirect unauthenticated visitors to `/login`.
- `about/page.tsx` "Open source / Apache 2.0 licensed" card updated to "Source available" - pending AGPL-3.0 licence file at PR 120.

**Problems encountered:**

### Decision - Licence: AGPL-3.0

**Decision:** The project will use AGPL-3.0, not Apache 2.0 or MIT.

**Rationale:** Apache 2.0 allows anyone to fork, rebrand and ship commercially without crediting the original author in any visible way. AGPL-3.0 requires anyone running the software as a network service to publish their source code under the same terms, and requires copyright notices to remain intact. This prevents silent commercial forks and ensures the project cannot be claimed as someone else's work.

**What changes:**

- `frontend/app/about/page.tsx` - "Open source / Apache 2.0 licensed" changed to "Source available" (will update to "AGPL-3.0 licensed" once the LICENSE file is in place at PR 120)
- `prompts/NEXT.md` PR 120 entry updated from "Apache 2.0" to "AGPL-3.0", branch renamed to `feat/license-agpl`
- PR 120 will add: `LICENSE` (full AGPL-3.0 text), `NOTICE` (copyright line), README licence badge
