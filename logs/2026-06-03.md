### 41. About + blog + changelog + docs hub pages (PR 115)

**Goal:** The platform had no public-facing information pages - no way to explain what it is, how it works, or where to find documentation. Steps 29, 33, and 34 of the plan.

**Design decisions:**

- `react-markdown` chosen over a custom markdown parser because the changelog page needs to render an existing `.md` file from the repo root. Server-side with `fs.readFileSync` at build time keeps the page static with zero runtime overhead.
- `@tailwindcss/typography` installed alongside `react-markdown` so the rendered markdown gets proper prose styling (heading hierarchy, code blocks, lists) without writing a custom stylesheet. The `prose` classes are only applied on the two markdown-rendered pages (changelog and blog post detail) - not on the about or docs hub pages which use hand-crafted Tailwind layouts.
- Blog post metadata (title, date, slug, excerpt, tags) is kept in two places: the markdown frontmatter (for the post page) and a hardcoded `POSTS` array in `blog/page.tsx` (for the index). Duplicating it is intentional - reading frontmatter from all files on every request just to render an index would be wasteful for a static list. If the blog grows past ~10 posts, a proper content pipeline (gray-matter + generateStaticParams) would be the upgrade path.

- Changelog page reads `../../CHANGELOG.md` relative to `process.cwd()` (which is `frontend/` at Next.js build time). Wrapped in a try/catch so a missing CHANGELOG gracefully degrades to a "not available" message rather than a build failure.

### Decision - Licence: AGPL-3.0

**Decision:** The project will use AGPL-3.0, not Apache 2.0 or MIT.

**Rationale:** Apache 2.0 allows anyone to fork, rebrand and ship commercially without crediting the original author in any visible way. AGPL-3.0 requires anyone running the software as a network service to publish their source code under the same terms, and requires copyright notices to remain intact. This prevents silent commercial forks and ensures the project cannot be claimed as someone else's work.

### 47. Vercel Analytics + GA4 (PR 120)

**Goal:** Step 28 of the plan. No analytics were firing in production - no pageview data, no event tracking. Vercel Analytics gives instant deployment-level insights. GA4 adds event tracking but must be gated behind cookie consent (GDPR requirement).

**Design decisions:**

- `@vercel/analytics` installed and `<Analytics />` placed directly in layout.tsx outside `<ToastProvider>`. The component is a server-safe thin wrapper - Vercel injects the tracking snippet at the edge so there is nothing to consent-gate for it.
- GA4 is handled by a separate `GoogleAnalytics.tsx` client component rather than inline Script tags in layout.tsx. The consent check requires `localStorage` which is only available in the browser, so the component must be a client component. Keeping it separate avoids making layout.tsx a client component unnecessarily.
- `GoogleAnalytics` reads `cookie_consent` from localStorage on mount. It also listens for `storage` events so consent changes in another tab propagate immediately without a page reload.
- GA4 tags only render when both `NEXT_PUBLIC_GA_ID` is set and consent is `'accepted'`. If either condition is false the component returns null with no DOM output. This means the build is safe with no GA4 ID configured (local dev, staging).
- `anonymize_ip: true` passed in the gtag config call as a belt-and-braces measure alongside the consent gate.
- `NEXT_PUBLIC_GA_ID` is set in the Vercel dashboard, not in any committed file. Local `.env.local` can set it for testing but that file is gitignored.

**Problems encountered:** None - lint and build clean on first run.

**Files changed:**

- `frontend/package.json` / `package-lock.json` - added `@vercel/analytics@^2.0.1`
- `frontend/components/GoogleAnalytics.tsx` - NEW. Client component. Reads `cookie_consent` from localStorage, listens for storage events, conditionally renders GA4 Script tags only when consent is accepted and `NEXT_PUBLIC_GA_ID` is set.

### 53. CodeQL, stale workflow and FUNDING.yml (PR 127)

**Goal:** Step 30 of the plan. The repo was made public on 2026-06-03. With the repo public, CodeQL code scanning is now available at no cost. Adding it means every push and PR to main is automatically scanned for security vulnerabilities in both the Python backend and JavaScript frontend. The stale workflow keeps the issue tracker clean as community contributions start arriving. FUNDING.yml adds a Sponsor button to the repo pointing at Patreon.

**Design decisions:**

- CodeQL runs on push and PR to main, and on a weekly Monday 08:00 UTC schedule. The weekly schedule ensures security findings surface even in quiet periods with no commits - without it, a dormant repo would never re-scan after the last push.
- Matrix strategy with `fail-fast: false` so a Python analysis failure does not cancel the JavaScript job. Both results are independent and both should always run.
- `autobuild` action used for both languages. For Python (interpreted) this is a no-op effectively - CodeQL just reads the source. For JavaScript it runs the Next.js build so CodeQL can analyse the compiled output. This is the correct approach for a Next.js project.
- `security-events: write` permission is required for CodeQL to upload SARIF results to the GitHub Security tab. `actions: read` and `contents: read` are the minimum additional permissions needed.
- Stale workflow runs daily at 01:00 UTC - early enough that any notifications land before the working day starts in most timezones, but not during peak hours.
- 60-day stale threshold is intentionally generous. This is a small open-source project where issues may sit for a while legitimately. A 14-day grace period after the stale label gives contributors reasonable time to respond.
- `exempt-issue-labels: pinned,security,in-progress` prevents the stale bot from touching security disclosures or work that is actively being tracked. The `security` label exemption is especially important - a security issue must never be auto-closed.
- Stale messages are written in plain English and explain what will happen and what the user can do to prevent closure. They do not use hostile or dismissive language.
- FUNDING.yml lists two platforms: `patreon: zaccesss` and `buy_me_a_coffee: zaccesss`. GitHub renders both as a Sponsor button on the repo page. No other platforms are configured - adding empty/placeholder entries for platforms not in use would be misleading.

**Problems encountered:** None - no CI to run for workflow-only files.

**Files changed:**

- `.github/workflows/codeql.yml` - NEW. CodeQL analysis on push/PR/weekly schedule, matrix over python and javascript
- `.github/workflows/stale.yml` - NEW. Daily stale job - 60 days to stale, 14 days to close, security/pinned/in-progress labels exempt
- `.github/FUNDING.yml` - NEW. Patreon and Buy Me a Coffee sponsor buttons (zaccesss)
