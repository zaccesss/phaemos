## Full project history (carried forward from LOG.md)

### Project identity

**Name:** PHAEMOS
**Pronunciation:** FAY-mos
**Meaning:** coined from Ancient Greek roots tied to revelation/appearance and structure/order - "an ordered system that reveals"
**Tagline:** Reveal before failure.

**What it is:** A full-stack IoT predictive maintenance platform. Physical sensors on machines send periodic readings through custom embedded firmware to a cloud backend. The backend ML-scores every reading, evaluates alert thresholds, creates maintenance tickets and streams live data to a real-time dashboard.

**Why it is notable:** End-to-end system ownership. Every layer built from scratch - embedded C++/Arduino firmware, Python REST API, relational database schema, unsupervised ML pipeline, real-time React frontend, full DevOps layer. Nothing is stubbed or mocked.

---

### Full system architecture

```
Physical world
  [DHT22] temperature + humidity
  [MPU6050] vibration / acceleration / gyroscope
  [LDR] ambient light (analogue, 0-1023 ADC)
  [DS18B20] precise 1-Wire temperature
       |
Firmware layer
  Arduino Uno  -- reads DHT22 + LDR + DS18B20
               -- serialises to UART: "TEMP:23.4,HUM:61.2,LIGHT:512"
               -- baud 9600 to ESP32

  STM32        -- MPU6050 via I2C at 100 Hz (10 ms interval)
               -- outputs: "VX:0.1200,VY:-0.0400,VZ:9.8100\r\n"
               -- I2C on hi2c1, UART on huart2

  ESP32        -- reads its own DHT22 + MPU6050 + LDR
               -- receives serial from Arduino and STM32
               -- posts JSON to backend over Wi-Fi
               -- on boot: checks for OTA firmware update first
       |
Network: HTTP POST (JSON, X-API-Key header)
       |
Backend: FastAPI / Python 3.11
  Receives telemetry -> ML scores -> evaluates alert rules
  -> persists to PostgreSQL -> broadcasts to WebSocket clients
  -> fires Discord/email notifications on critical/warning alerts
       |
Databases: PostgreSQL 15 + Redis 7
       |
Frontend: Next.js 15 / TypeScript
  Real-time telemetry via WebSocket
  Devices, alerts, tickets, admin (OTA upload) pages
```

---

### Database schema

All primary keys are PostgreSQL UUID generated by `uuid.uuid4()`. Foreign keys cascade on delete from `devices.id`. Timestamps use `timezone=True` with `server_default=func.now()`.

**devices:** id, name, location, type (esp32/arduino/stm32), api_key (unique), status (online/offline/warning/fault), last_seen, created_at

**telemetry:** id, device_id FK, temperature, humidity, vibration_x/y/z, light_level, anomaly_score (0-1 normalised), is_anomaly (True when score >= 0.7), recorded_at

**alert_rules:** id, device_id FK, metric, condition (gt/lt/eq), threshold, severity (info/warning/critical), created_at

**alerts:** id, device_id FK, rule_id FK (nullable - NULL for ML anomaly alerts), message, severity, resolved (String column - pre-existing type bug), triggered_at, resolved_at

**tickets:** id, device_id FK (nullable), alert_id FK (nullable), title, description, status (open/in_progress/closed), priority (low/medium/high/critical), assigned_to UUID FK (nullable), created_by UUID FK (nullable - Phase 2), created_at, updated_at

**users:** id, name, email (unique), password_hash (bcrypt cost 12), role (admin/technician/viewer, default viewer), created_at, last_login

**audit_logs:** planned Phase 2

### API routes

All REST at `/api/v1`. WebSocket at `/ws`. Health at `/`.

Auth: POST /auth/register (201), POST /auth/login (200 + JWT), GET /auth/me (501 - Phase 2)
Devices: GET/POST /devices, GET/PATCH/DELETE /devices/{id}
Telemetry: POST /telemetry (ingest, X-API-Key), GET /telemetry/{device_id}, GET /telemetry/{device_id}/latest
Alerts: GET /alerts, GET /alerts/{device_id}, PATCH /alerts/{id}/resolve, POST /alert-rules
Tickets: GET/POST /tickets, GET/PATCH /tickets/{id}

Firmware: POST /firmware/upload, GET /firmware/latest, GET /firmware/download
WebSocket: WS /ws/telemetry/{device_id}
Health: GET / (status + version + environment), GET /metrics (Prometheus)

### Auth system

**User auth:** JWT bearer tokens via python-jose. HS256. Payload: `{sub, role, exp}`. bcrypt cost 12 for passwords. Tokens stored in localStorage on frontend (XSS risk - tracked in suggestions).

**Device auth:** Static X-API-Key header. `secrets.token_urlsafe(32)` at registration. Stored plaintext in devices.api_key for direct lookup on every ingest.

**Roles:** admin (all), technician (alerts + tickets), viewer (read-only). New users default to viewer.

---

### ML pipeline

Algorithm: Isolation Forest (scikit-learn, unsupervised).
Parameters: n_estimators=200, contamination=0.05, random_state=42.
Features: raw 6 sensors + rolling mean/std (window=10) + time_of_day fraction.
Score normalisation: `clip(1 - (raw_score + 0.5), 0.0, 1.0)`. Threshold: 0.7.
Before training: returns (0.0, False) - system operates normally.
Training: `python ml/train.py --csv telemetry_export.csv`. Outputs model.pkl (gitignored).

---

### Firmware

**ESP32:** DHT22 + MPU6050 + LDR. Posts JSON to backend over Wi-Fi every 5 seconds. On boot checks OTA update. Libraries: Adafruit DHT, MPU6050, ArduinoJson, HTTPClient, HTTPUpdate.

**Arduino Uno:** DHT22 + LDR. Serial output format: `TEMP:23.4,HUM:61.2,LIGHT:512`. Baud 9600 to ESP32.

**STM32:** MPU6050 at 100 Hz via I2C (HAL). UART format: `VX:0.1200,VY:-0.0400,VZ:9.8100\r\n`. Register-level driver: addr 0x68, PWR_MGMT_1 0x6B, ACCEL_XOUT 0x3B, scale 16384.0f (+/-2g).

### Key design decisions (from docs/decisions.md, dated 2026-04-23)

001: Isolation Forest over supervised ML - no labeled data at start
002: Device API keys over JWT - firmware cannot manage token refresh
003: Monorepo - easier to demonstrate full system for portfolio
004: Poll-based frontend -> superseded by WebSocket 2026-05-22
005: PostgreSQL from day 1 - dev/prod parity, UUID types require it
