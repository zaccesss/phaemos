### 19. Webhooks backend - Slack/Discord/Teams integrations (PR 95)

**Goal:** Alert notifications only lived in the UI. Enterprise teams need to be paged wherever they work - Slack, Discord, Teams. The existing `notify_service.py` already had a single hardcoded Discord URL from settings; this replaces that pattern with a proper per-webhook DB table so admins can add/remove/toggle any number of outbound hooks from the admin UI without redeploying.

**Design decisions:**

- Chose a DB table (`webhooks`) over a JSON config file because the admin UI needs to CRUD webhook entries at runtime. A config file would require a restart.
- Three platforms auto-detected from URL pattern: Discord (`discord.com/api/webhooks`), Teams (`webhook.office.com`), and Slack (default). All three accept similar JSON shapes so one service handles all - Discord wants `{"embeds": [...]}`, Teams wants `{"@type": "MessageCard", ...}`, Slack/generic wants `{"text": "..."}`. I detect the platform from the URL so admins just paste their webhook URL without choosing a type.
- Added a `template` TEXT column (nullable) for custom message bodies. When NULL, the built-in `"[PHAEMOS] {severity}: {metric} on {device_name} = {value} (threshold: {threshold})"` format is used. Admins can override with any string containing those placeholders. Nullable is correct because the default template lives in code, not the DB - a non-null constraint would force every row to store a duplicate of the default.
- Retry-once on delivery failure. I chose one retry rather than a queue or exponential backoff because this runs synchronously inside the alert evaluation flow. If the remote webhook is down, we do not want to hold up telemetry ingestion. One retry handles transient HTTP blips; persistent failure just logs a warning. The alert is still saved to DB regardless.
- `notify_all` called from `alert_service.evaluate_rules` after the alert row is added to the session (but before `db.commit()`). The call is fully synchronous - no background task - because the telemetry ingest endpoint already returns 200 immediately and the alert evaluation runs as a FastAPI `BackgroundTask`. So we are already off the critical path.

**Files changed:**

- `backend/migrations/006_webhooks.sql` - NEW. Creates the `webhooks` table: `id` (UUID PK), `name` (VARCHAR 200 NOT NULL - human label for the UI), `url` (TEXT NOT NULL - the full webhook URL), `enabled` (BOOLEAN NOT NULL DEFAULT TRUE - admins can pause a hook without deleting it), `template` (TEXT nullable - custom message format), `created_at` (TIMESTAMPTZ with server default). IF NOT EXISTS guards make it idempotent so it is safe to re-run during a partial migration.
- `backend/app/models/webhook.py` - NEW. `Webhook` SQLAlchemy ORM model mapping to the `webhooks` table. The `template` column uses `nullable=True` because NULL means "use the built-in default", not "missing data".
- `backend/app/services/webhook_service.py` - NEW. Core logic: `_is_discord()` and `_is_teams()` pattern-match the URL to choose payload format. `_build_payload()` constructs the platform-specific JSON. `_deliver()` POSTs with a 5-second timeout and retries once on failure; exceptions are caught and logged as warnings so a broken webhook never raises and never blocks the alert flow. `notify_all(db, context)` queries all enabled webhooks and calls `_deliver` for each. `test_webhook(wh)` fires a fixed test message and returns True/False - used by the admin test button endpoint.
- `backend/app/routes/webhooks.py` - NEW. Admin-only routes: `GET /api/v1/webhooks` (list, ordered by created_at desc), `POST /api/v1/webhooks` (create, 201), `PATCH /api/v1/webhooks/{id}` (update name/url/enabled/template), `DELETE /api/v1/webhooks/{id}` (204). Plus `POST /api/v1/webhooks/{id}/test` which calls `webhook_service.test_webhook()` synchronously and returns `{"success": true/false}`. All require `require_admin` - webhook config is infrastructure-level.
- `backend/app/services/alert_service.py` - Added `from app.services import webhook_service` import and `webhook_service.notify_all(db, {...})` call inside the per-rule loop, immediately after the legacy `notify_service` calls. ### 20. Fleet health summary and public status endpoint (PR 96)

**Goal:** No fleet-level health score existed. The dashboard had no single-glance "is everything OK?" indicator. Also needed a machine-readable `/status` endpoint for uptime monitoring (Uptime Kuma already configured per `docs/uptime-kuma.md`).

**Design decisions:**

- Two separate routers (`router` and `public_router`) in the same file rather than one router with different auth guards per route. I chose this because FastAPI's `include_router` takes a single prefix and auth dependencies are set at the route level - by registering `public_router` without a prefix and `router` with `/api/v1`, the `/status` endpoint sits at the root (`/status`) with no auth, while `/api/v1/health/summary` requires a token. If I had used one router, I would have needed to mix `Depends(get_current_user)` with no-auth on the same router object which is messier.
- Health score formula: `round((online/total) * 100 * (1 - min(active_alerts/max(total_rules, 1), 0.5)))`. The formula penalises alert noise up to 50% - a fleet with all devices online but half its rules firing gets a score of 50, not 100. I cap the penalty at 0.5 so the score can never reach 0 just from alerts on a fully-online fleet; a score of 0 requires devices to be offline.
- `total_rules` is used as the denominator for alerts rather than total alerts ever - this prevents a fleet with no rules configured from getting a penalty for zero-division. `max(total_rules, 1)` is the guard.
- Redis health check uses a lazy import (`import redis as redis_lib`) inside the function rather than a top-level import. I chose this because `redis` is an optional dependency not all environments have installed - a missing package would crash the whole app on startup if imported at module level. The lazy import means if redis is absent, `_check_redis()` catches the ImportError and returns `"error"` without breaking anything else.
- DB health check creates a fresh `SessionLocal()` rather than depending on `get_db()` because the `/status` endpoint takes no `db: Session` dependency (it is public/no-auth) and I did not want to add a DB dependency just for the health check - the session is created and closed in the function.

**Files changed:**

- `backend/app/routes/health.py` - NEW. Two APIRouter objects: `router` (auth-protected fleet stats) and `public_router` (public /status). `GET /health/summary` queries Device, Alert, Ticket, AlertRule counts and computes the health score formula. `GET /status` calls `_check_db()` (SELECT 1 via a fresh session) and `_check_redis()` (PING via lazy import), returns `"operational"` if both pass or `"degraded"` if either fails.
- `backend/app/main.py` - Added `from app.routes.health import router as health_router, public_router as health_public_router`. Registered `health_router` under `/api/v1` (authenticated) and `health_public_router` at root level (public `/status`).

**Problems encountered:** Initial registration used the same router object twice with different prefixes. This worked but was confusing and registered the `/status` route at both `/api/v1/status` and `/status`. Fixed by splitting into two distinct router objects. PR 96 had a CI-wait delay (~90 seconds) before auto-merging.

### 21. Maintenance windows backend with alert suppression (PR 97)

**Goal:** Planned downtime generates alert noise. When a technician schedules maintenance on a device, every sensor reading that crosses a threshold fires an alert, creating dozens of false-positive tickets. Maintenance windows suppress that noise for the duration of the window.

**Design decisions:**

- `device_id` is nullable (NULL = fleet-wide window). This lets admins schedule a window for "all devices during the weekend upgrade" without having to create one window per device. The `is_in_maintenance` helper uses `OR (device_id = ? OR device_id IS NULL)` so a fleet-wide window suppresses all devices.
- `suppress_alerts` is a boolean column on the window itself rather than always-suppressing. I added this so future use cases could use maintenance windows for scheduling (e.g. "show this window in the UI") without suppressing alerts - the flag makes the behaviour configurable.
- `ON DELETE CASCADE` for `device_id` FK - when a device is deleted, its maintenance windows should also be deleted. There is no reason to keep an orphaned window for a device that no longer exists.
- `ON DELETE SET NULL` for `created_by` FK - when a user is deleted (GDPR erasure), we keep the maintenance windows because they are operational records. Setting `created_by = NULL` preserves the window without blocking the user deletion.
- Two indexes: one on `device_id` (for the `WHERE device_id = ?` filter) and one on `(start_at, end_at)` (for the active-window time range filter). The composite index means `WHERE start_at <= now AND end_at >= now` can use an index scan rather than a full table scan.
- `is_in_maintenance()` is in the routes file rather than the services file because it is a DB query that returns a boolean - it is closer to a "query helper" than a "service". It is imported by `alert_service.py` which lives in `services/`. This is a slight layering violation but acceptable at this scale.
- The check in `alert_service.evaluate_rules` is at the top of the function, before the rule loop. I chose early return rather than checking per-rule because: (a) if a device is in maintenance, suppressing ALL its alerts is the desired behaviour, and (b) it saves the DB query for all rules when the device is in maintenance.

**Files changed:**

- `backend/migrations/007_maintenance_windows.sql` - NEW. Creates `maintenance_windows` table with all columns as described above. `GIN` index on... wait, actually two B-tree indexes: `ix_maintenance_windows_device_id` on `device_id` and `ix_maintenance_windows_start_end` on `(start_at, end_at)`. IF NOT EXISTS guards for idempotency.
- `backend/app/models/maintenance.py` - NEW. `MaintenanceWindow` SQLAlchemy model. All FKs use `nullable=True` (device_id for fleet-wide, created_by for GDPR safety). `suppress_alerts` defaults to True since suppression is the whole point of a maintenance window.
- `backend/app/routes/maintenance.py` - NEW. `GET /maintenance-windows` with `Depends(get_current_user)` so any authenticated user can see the schedule. `POST`, `PATCH`, `DELETE` all require `require_admin`. `POST` validates `end_at > start_at` and raises 400 if not. `PATCH` re-validates the time constraint after applying updates. `is_in_maintenance(db, device_id)` exported from this module - takes a `Session` and `UUID`, queries for any window where `start_at <= now() <= end_at AND suppress_alerts = true AND (device_id = passed_id OR device_id IS NULL)`.

### 22. Device tags + batch operations backend (PR 98)

**Goal:** Three gaps existed: (1) no way to label/group devices (e.g. "production" vs "staging"), (2) no way to search or filter devices by name or status in the API, and (3) no way to push a firmware update to a group of devices at once - you had to update each device individually. All three are table-stakes for a multi-device fleet.

**Design decisions:**

- PostgreSQL `TEXT[]` array column for tags rather than a join table (`device_tags` with `device_id + tag` rows). I chose the array because: the tag set per device is small (typically <10 tags), queries using `tag = ANY(tags)` with a GIN index are fast at our scale, and the simpler schema means fewer JOINs in list queries. A join table is only worth the complexity when tags need their own metadata (colour, description, created_at) or when the cardinality is high - neither applies here.
- `server_default="{}"` on the column so existing rows (created before this migration) automatically get an empty array instead of NULL. Combined with `NOT NULL` this guarantees the field is always a list, never None, so callers do not need to null-check.
- GIN index (`CREATE INDEX ... USING GIN(tags)`) on the tags column specifically for the `tag = ANY(tags)` filter in `GET /devices?tag=`. GIN is the right index type for array containment queries in PostgreSQL; a standard B-tree index does not support array operators.
- `search` query param uses `ILIKE '%query%'` on `Device.name`. Case-insensitive partial match is the expected UX. I put the filter in the route query rather than loading all devices and filtering in Python to keep it efficient at scale.
- `status` filter passes directly to `Device.status == status`. No validation of the status value at the API level - if an unknown status is passed, the query just returns zero results, which is the correct behaviour (not a 400).
- Tag add/remove endpoints (`POST /devices/{id}/tags`, `DELETE /devices/{id}/tags/{tag}`) use list concatenation: `device.tags = device.tags + [new_tag]` for add and `device.tags = [t for t in device.tags if t != tag]` for remove. I chose this over SQL `ARRAY_APPEND`/`ARRAY_REMOVE` functions because SQLAlchemy's ORM change-detection works reliably with Python-level reassignment of the full array; using SQL functions would bypass the ORM's dirty-tracking and require `flag_modified()` calls.
- `POST /devices/batch/firmware-update` sets `firmware_version` on all matching devices rather than queuing a separate job. Devices call `/firmware/latest` on a polling interval and get the new version; the existing OTA mechanism already handles the rest. This is deliberately simple - no queue, no tracking of "who acknowledged the update". A proper job queue is a hardware-blocked enhancement (needs devices to report back).

**Files changed:**

- `backend/migrations/008_device_tags.sql` - NEW. `ALTER TABLE devices ADD COLUMN IF NOT EXISTS tags TEXT[] NOT NULL DEFAULT '{}'` followed by `CREATE INDEX IF NOT EXISTS ix_devices_tags ON devices USING GIN(tags)`.
- `backend/app/models/device.py` - Added `from sqlalchemy.dialects.postgresql import ARRAY, UUID` (ARRAY was new). Added `tags = Column(ARRAY(String), server_default="{}", nullable=False)` after the `owner_id` column.

### 23. Refresh token interceptor + withCredentials in api.ts (PR 18 - frontend sprint start)

**Goal:** The backend issues 15-minute access tokens with httpOnly refresh cookies. Without an interceptor, a user whose token expires mid-session hits a 401 and gets bounced to /login. This is disruptive and unnecessary - the refresh cookie is valid for 7 days and can silently renew the access token in the background without the user noticing.

**Design decisions:**

- `withCredentials: true` on the axios instance so the httpOnly refresh cookie is sent cross-origin on every request. Without this the browser strips cookies on cross-origin calls and the refresh endpoint would never receive the cookie.
- Single `isRefreshing` module-level flag to prevent the thundering-herd problem: if multiple requests 401 simultaneously (e.g. the user loads a page with four concurrent API calls and the token just expired), only the first one triggers the refresh flow. The others are rejected immediately (`if (isRefreshing) return Promise.reject(error)`). In a more complex app I would queue the subsequent requests and replay them after the refresh completes, but at Phaemos' current scale (one session per user, small number of concurrent calls per page load) a simple flag is sufficient and far less complex.
- `originalRequest._retry = true` guard prevents an infinite loop: if the /refresh call itself returns 401 (e.g. the refresh token is also expired or revoked), we do not retry, we clear localStorage and redirect to /login.
- On refresh failure, `localStorage.removeItem('token')` then `window.location.href = '/login'` - hard navigation rather than a Next.js router push. I chose this because the user may be in any page and a hard navigation is guaranteed to reset all component state including any stale auth context. A soft push might leave stale components that still reference the expired token.
- The fallback `return Promise.reject(error)` after the try/catch is required - without it, the interceptor would swallow the error on refresh failure and callers would hang waiting for a response that never resolves.

**Files changed:**

- `frontend/lib/api.ts` - Added `withCredentials: true` to the axios instance. Added `isRefreshing` module-level flag. Added response interceptor: on 401, sets `_retry`, calls `/auth/refresh` with `withCredentials: true`, stores the new token, retries the original request. On refresh failure, clears token and redirects to /login.

### 25. Advanced RBAC - per-user permissions column and endpoint (PR 101)

**Goal:** Role-based access control via `admin`/`technician`/`viewer` is coarse. Some technicians need to manage devices they do not own, or resolve alerts, without being elevated to full admin. A per-user `permissions` JSON override lets admins grant specific capabilities without a full role change.

**Design decisions:**

- Chose `JSONB` (not `JSON`) for the column because PostgreSQL can index JSONB and GIN-path queries are faster. At this scale it makes no practical difference but it is the correct default for any JSON column you might ever filter on.
- `NULL` means "use role defaults only". An explicit empty object `{}` would mean "override with nothing" - that distinction matters for future Phase 2 RBAC where you might want to explicitly strip a default permission. So NULL is the right sentinel for "not configured".
- Recognised capability keys: `can_manage_devices`, `can_resolve_alerts`, `devices_scope` (array of device UUIDs). These are checked in `get_current_user`'s downstream callers as needed - the column is intentionally schema-free so new capabilities can be added without migrations.
- The `PATCH /auth/users/{id}/permissions` endpoint is admin-only. It accepts a dict and overwrites the entire `permissions` field (last-write-wins). This is intentional - permissions are small and treating them atomically avoids partial-update races.
- Passing `null` as the body clears all permissions and reverts the user to role defaults. This is the "reset" path.

**Files changed:**

- `backend/app/models/user.py` - Added `JSON` to SQLAlchemy imports. Added `permissions = Column(JSON, nullable=True)` after `totp_enabled`.
- `backend/migrations/009_rbac_permissions.sql` - NEW. `ALTER TABLE users ADD COLUMN IF NOT EXISTS permissions JSONB`.
- `backend/app/routes/auth.py` - Added `uuid` and `typing.Any` imports. Added `PATCH /auth/users/{id}/permissions` admin-only endpoint that reads the UUID from the path, looks up the user, replaces `user.permissions` with the request body dict (or None to clear), commits, and returns the updated `UserResponse`.
- `backend/app/schemas/user.py` - Added `typing.Any` import. Added `permissions: dict[str, Any] | None = None` to `UserResponse` so callers can see the current permission overrides.

### 28. User invitation flow via Resend email (PR 104)

**Goal:** Admins can only create accounts via the register endpoint, which requires the invitee to already know the URL. A proper invite flow lets admins send a signed link to any email address; the invitee clicks the link, sets a password, and their account is activated automatically.

**Design decisions:**

- Invite token is a JWT with `type: "invite"`, 48-hour expiry, and both `email` and `role` embedded. Embedding the role means the accept endpoint assigns it directly without a second DB lookup.
- `POST /auth/invite` returns the invite link in the response body as well as sending the email - useful in dev where Resend is not configured.
- Accept link built from `request.base_url`, replacing port 8000 with 3000 to point at the Next.js frontend.
- `email_service.send_invite()` falls back to logging the link at INFO level when `RESEND_API_KEY` is placeholder. No credentials required to test in dev.
- `GET /auth/accept-invite/{token}` validates the token before the user fills in the form so the frontend can show a "link expired" error upfront.
